# redundant-type-conversion (TRI006): `ty`-driven detection over LSP

## Context

A builtin type-conversion call — `int(x)`, `list(x)`, and similar — is sometimes a no-op given the real, statically-known type of `x`. The only existing tooling that catches any part of this (pyrefly's `unnecessary-type-conversion`) only catches the trivial same-scope case, only for scalar builtins, and misses the more valuable cross-file call-site case entirely (confirmed empirically, not assumed — see the tool comparison below). Catching the cross-file case needs real, resolved type information; a local AST-only heuristic would mean re-implementing a subtyping/assignability engine, which this project's own architecture principles rule out as a maintenance burden and a correctness risk versus delegating to a real type checker.

## Tool selection

`ty`, `pyrefly`, `pyright`, and `mypy`/`dmypy` were measured against this repo's own size for query capability, latency, and daemon requirements. Full method and figures: `docs/audits/type-checker-selection-for-redundant-type-conversion.md`.

`ty` was chosen: fastest in every measurement taken (fresh-CLI and fresh-LSP alike), the cheapest recheck-cycle cost of the four, and the only one needing no daemon-lifecycle engineering to clear this project's existing performance budget (<1s best case, <3s worst case). Its main carried risk — explicitly pre-1.0, "no stable API, breaking changes possible between any two versions" per its own docs — is mitigated by the self-test below rather than assumed away.

## Decision

### Invocation

One `ty server` LSP session is kept alive for a whole hook invocation (not spawned per file or per query), driven by a hand-rolled, standard-library-only JSON-RPC client (`pre_commit_hooks._lsp`) — no third-party LSP client dependency, matching `docs/adding-a-check.md`'s "standard library only" rule for every check. The session is created lazily, on the first file with at least one real, non-suppressed AST-level candidate (see `candidates.find_candidates`), not at CLI startup and not merely on the first file whose prefilter match happens to be a false positive (e.g. `print(1)` matching the `"int("` prefilter pattern) — a run with nothing for this check to actually flag never pays `ty`'s startup cost.

### Detection method

Hover cheaply narrows which candidates are even worth the more expensive step; a synthetic in-memory rewrite (removing the wrapping conversion) plus a diagnostic recheck decides actual redundancy, by diffing "before" and "after" diagnostics rather than requiring either snapshot to be literally empty — an unrelated diagnostic present in both is not a signal either way. This drives `ty`'s own real assignability engine instead of reimplementing subtyping/protocol-satisfaction logic locally, which is what lets the same mechanism catch both the trivial same-scope case and the harder cross-file call-site case uniformly.

Detection is scoped to a call whose entire syntax — constructor name through closing paren — sits on one physical line. The rewrite splices out just the wrapping call syntax on that line; restricting this to single-line calls guarantees every other line's numbering stays intact, which the diagnostic diff depends on to mean anything. A multi-line-wrapped call is left out of this check's coverage rather than risking a wrong verdict from a shifted line number.

An argument whose own text ends inside a nested call's parentheses (e.g. `list(get_items())`, or `str(a or get_default())`) is also excluded from candidacy: `ty`'s hover reports the type of whichever token's own span contains the queried position, never a `Call` node's synthesized return type — hovering anywhere inside a nested call resolves to the callee's own signature, or (nearer the closing paren) its last argument's own type, instead (confirmed empirically against real `ty`). Without this exclusion, a candidate like this could be reported with a wrong, sometimes wildly unrelated `argument_type` in its message, and — at `conservative` level, where the hover gate requires an exact textual match — silently missed even when genuinely redundant, since the wrong hover text would never match the constructor's own name.

A `GeneratorExp` argument (e.g. `tuple(x for x in y)`, parenthesized or not) is excluded outright, independent of any hover-position concern: a generator expression's own runtime type is never any of these eleven constructors', so wrapping one in `tuple(...)`/`list(...)`/etc. is never actually redundant — there's no shape where "the argument is already a `tuple`" could apply to something that's syntactically a generator expression. This exclusion would be needed on that basis alone, but a bare (unparenthesized) generator additionally carries the same hover-position hazard as the nested-call case above, for a distinct reason: Python's own grammar gives a `GeneratorExp` used as a function's sole, unparenthesized argument the _same_ end position as the enclosing call itself (confirmed via `ast.parse` directly — `arg.end_col_offset == call.end_col_offset`; the generator's own explicit parens, as in `tuple((x for x in y))`, change this). Hovering one character before the argument's own end then lands on the conversion call's own closing paren rather than anywhere inside the generator, resolving inconsistently there — confirmed empirically, sometimes to the last sub-expression's real type, sometimes to the constructor's own signature (e.g. `class tuple(iterable: Iterable[Unknown] = ..., /)`) depending on what precedes it.

`ty`'s hover response for a symbol that carries its own docstring (a class, function, or similar) appends that docstring after a fixed dashed-line separator in the same response value — confirmed empirically to be a constant-length line, not derived from the signature's own length, so it's reliably distinguishable from the type/signature text itself. `TySession.hover()` keeps only the text before that separator; without this, a candidate whose argument is a bare class/function reference (e.g. `set(SomeEnum)`) would carry that reference's entire docstring, verbatim, into the reported message's `argument_type`.

### Confidence tiering

`--redundant-type-conversion-level={conservative,permissive}` (default `conservative`) controls two independent axes:

- **Which constructors are candidates at all.** `conservative` considers only the seven whose results avoid mutable-copy semantics (`str`/`int`/`float`/`bool`/`bytes`/`frozenset`/`tuple`): none of them ever produces a mutable result, so removing the call can never turn a distinct, mutable copy into a shared, mutable reference. `tuple` and `frozenset` do return the identical object as their argument when it's already exactly that type (confirmed empirically: `tuple(t) is t` and `frozenset(fs) is fs` for an already-exact `t`/`fs`) — but since both are immutable, that shared identity is inert; there's no mutation path through which it could matter. `permissive` also considers the four copy-producing constructors (`list`/`dict`/`set`/`bytearray`) — the type checker's assignability recheck can confirm type-redundancy for these too, but can't distinguish that from a genuine aliasing/mutation-safety change (a copy becoming a shared reference), so this is an explicit, opt-in trade-off rather than a default-on one.
- **How strictly the hover pre-filter accepts a candidate before paying for the recheck.** `conservative` requires an exact match between the argument's own inferred type and what the constructor would produce — including a flow-narrowed `Literal[...]` of the same scalar (`ty` reports a variable's narrowed value at a given point, not just its wider declared annotation), matched by the literal's own textual spelling rather than runtime subtyping so that `bool`/`int` — a real subtype relationship that would otherwise let `int(some_bool)` slip through as if it were a no-op — are never conflated. `permissive` accepts any resolved, non-`Any` type, which is what lets a structural/protocol-satisfying match (e.g. `list[str]` satisfying an `Iterable[str]` parameter) through to the recheck — hover alone cannot decide that shape (see the audit's "Hover alone is not enough" finding), so `permissive` simply defers to the recheck's own verdict instead of pre-filtering on it. A union hover (`int | float`) is the one shape decided at the gate itself rather than deferred to the recheck: every member must individually pass the same exact-match test `conservative` uses, since "some member is compatible" isn't enough — `int(x)` where `x: int | float` genuinely truncates whenever `x` is actually a `float`, and the recheck's own sink is frequently too weak to notice that on its own (see the accepted limitation below). `Unknown` — `ty`'s own marker for a value it couldn't infer at all, e.g. an unannotated parameter or one flowing from an import it couldn't resolve — is rejected by the gate the same as `Any`, at both levels, including when narrowed (`Unknown & ~AlwaysFalsy`): it carries exactly as little information as `Any` does about whether wrapping the value is redundant.

A candidate that's the sole argument of an enclosing `len(...)` call gets one further, narrower rule on top of the above: `len()` accepts any `Sized` argument uniformly, so its own diagnostic-diff recheck can never discriminate one container type from another — `len(set(a_list))` looks exactly as "redundant" to that recheck as `len(a_list)` already being a `set`, even when the `set(...)` wrap is doing real, intentional work (deduplicating before counting, a common idiom). Unlike the general weakly-typed-sink gap below, this shape is narrow and structurally recognizable directly from the AST (`candidates._scan()`), so it isn't merely hedged in the message the way that gap's other instances are — a non-exact-match candidate wrapped this way is not reported at all. An exact match (e.g. `len(set(already_a_set))`) is still reported, since removing the conversion there is genuinely a no-op regardless of `len()`'s own blindness to it.

A `str(...)` (or other) conversion whose result feeds an `==`/`!=`/`in`/`not in`/`is`/`is not` comparison — bare, or as an element of a `list`/`tuple`/`set` literal operand, or a key/value in a `dict` literal operand — gets its own narrow exclusion when the wrapped value's hover names one of `pathlib`'s own concrete path classes (`Path`, `PurePath`, `PosixPath`, `WindowsPath`, `PurePosixPath`, `PureWindowsPath`). `PurePath.__eq__` returns `NotImplemented` for anything that isn't itself a `PurePath` — a stdlib behavior confirmed empirically, not assumed — so `some_path == "some_string"` is always `False` regardless of the string's content, whether compared bare or as a list/tuple/set/dict element; `is`/`is not` carries the same risk for an entirely different reason (a fresh `str(...)` call is never the same object as its argument, so removing the wrap flips an `is` comparison's result outright, independent of `PurePath.__eq__`). A `str(a_path)` conversion feeding such a comparison is therefore almost always load-bearing, not redundant, even though the recheck's own diagnostic-diff can't see that (`==`/`in`/`is` are all typed to accept `object`, so removing the wrap never produces a new diagnostic either). This is a real, well-known behavior of a single stdlib type rather than the general, unrecognizable-in-the-abstract weakly-typed-sink gap below, so it's excluded outright (`candidates._scan()`, `confidence.is_purepath_hover`) rather than merely hedged. Nesting is followed recursively through `list`/`tuple`/`set`/`dict` literals (e.g. `matches == [(str(a_path),)]`), not just their immediate elements.

Hover text alone carries no module provenance — a locally defined `class Path` would hover identically to `pathlib.Path` — so this exclusion is disabled for the whole file whenever any of those class names is bound to anything other than an ordinary `from pathlib import <Name>` (the same whole-module, scope-blind bias already used for every other name in `_scan()`, just narrowed to tolerate the one legitimate binding shape). A user-defined `PurePath` subclass under some _other_ name is a separate, unclosed gap: it isn't recognized at all, since hover text carries no base-class information either.

### Suppression

A candidate on a line already carrying `# pytriage: ignore=TRI006`, or a third-party type-suppression comment (`# type: ignore`, `# pyright: ignore`, `# ty: ignore`), is always skipped outright, at either confidence level, by inspecting the target file's own source — never by trusting `ty`'s own diagnostics to already reflect the suppression. The synthetic rewrite preserves line numbers, so a pre-existing suppression comment would otherwise keep masking the recheck's own signal after the conversion is stripped, misreporting a genuinely necessary conversion as redundant; this was confirmed as a real, reproducible failure mode during development, not a theoretical concern.

### Failure handling

`check()` can raise a new `CheckUnavailableError` (see `docs/adr/0034-cacheable-check-flag-and-always-rerun-orchestrator-split.md` and `docs/adr/0036-check-unavailable-error-isolated-per-check.md` for the orchestrator-level handling this required) in two distinct cases, each with its own actionable message: `ty` isn't on `PATH` at all (install hint), or `ty` is present but fails this check's own behavioral self-test (version-mismatch hint, distinct from the install hint since the remediation differs). The self-test runs once per process, before the real session is ever handed out, using one redundant-case and one necessary-case fixture as positive/negative controls — because `ty`'s own versioning policy allows breaking changes to diagnostics between any two versions, the pinned dev-dependency floor documented for install purposes is not trusted alone at runtime.

### No autofix

This check is detect-only in this version. A wrong report costs a human a wasted look; a wrong _fix_ could silently change program behavior around aliasing/mutation for a copy-producing constructor, a risk not yet fully designed for. Autofix is deferred entirely.

## Consequences

- This check requires `ty` as a separately installed prerequisite (`uv tool install ty`, or a project's own dev dependency) — not bundled with `ruff-extra-rules`, not a runtime dependency. A user without it on `PATH` gets a loud, one-time, actionable failure instead of silent empty output.
- This check's own test suite is a hybrid: the bulk of its logic is unit-tested against recorded/fake session responses for speed and determinism; a small integration layer (`tests/test_redundant_type_conversion_integration.py`) runs against the real, pinned `ty` binary and shares one warm session across the whole test module, so a future `ty` version bump is automatically checked for recorded-fixture staleness on every CI run.
- Restricting detection to single-line-wrapped calls is a real, accepted coverage gap, not a soundness one — a multi-line-wrapped redundant conversion goes unreported rather than risking a false verdict.
- `ty`'s own pre-1.0 status remains the primary long-term risk this decision carries; the self-test is this check's own mitigation, not a guarantee that every future `ty` release stays compatible without a code change.
- The prefilter's fixed-string patterns (`"str("`, `"list("`, ...) require the constructor name and its opening parenthesis to sit together with no whitespace in between, so a call written as `str (value)` never reaches this check at all. This relies on the same repo-wide assumption AGENTS.md states for every check — every file has already passed `ruff format`, which always removes that whitespace — rather than this check defending against non-canonical formatting on its own.
- **Accepted limitation, not fixed**: hover reports an expression's _static_ type, which for a value annotated (or widened to) exactly `int`/`str`/`float`/`bytes`/`tuple`/`frozenset` also covers every runtime subclass of that type per Liskov substitution — a value statically typed `int` that's actually a custom `IntSubclass` instance at runtime looks identical to hover. `int(such_a_value)` genuinely normalizes it to a plain `int`, which removing the call would not. This is inherent to any purely static-type-based redundancy check (the same gap exists in pyrefly's own narrower `unnecessary-type-conversion` rule) — closing it would mean either reimplementing local subtype-flow tracking (the exact re-implementation this whole architecture exists to avoid) or restricting `conservative` mode to `Literal[...]` hovers only, which would gut it down to a small fraction of its current, useful cases. Left as a known trade-off: for a _custom_ subclass of an immutable builtin, it requires a codebase to both define that subclass and rely on a conversion's normalizing side effect, an unusual combination in practice. `bool` is not that unusual case, though — it's a builtin subclass of `int` (`class bool(int)`), so any `int`-annotated, non-narrowed parameter or variable that could actually hold `True`/`False` at runtime carries this same gap, and does so far more often in ordinary code than a custom subclass would. `_literal_matches_constructor` already distinguishes the two spellings for a _narrowed_ `Literal[True]`/`Literal[1]` hover; there is no equivalent distinction available once the hover has already widened to the bare `int`, since hover text alone can't tell "declared `int`, only ever assigned actual ints" apart from "declared `int`, sometimes passed a `bool`" without the same subtype-flow tracking this architecture avoids.
- **Accepted limitation, not fixed**: beyond a union (decomposed and checked member-by-member, see "Confidence tiering" above) and `Any`/`Unknown` (rejected outright), `permissive`'s hover gate still accepts any other single resolved argument type unconditionally, not just a genuine structural/protocol match — so the recheck can run, and find no new diagnostic, even when the argument's type has nothing to do with the constructor at all, whenever the surrounding context is itself too weakly typed to produce a diagnostic either way. Confirmed empirically: `def f(x: int) -> None: y: object = str(x)` and the same function with `str(...)` removed both pass `ty check` cleanly, even though `x` is an `int`, not a `str`, and removing the wrap genuinely changes `y`'s runtime type. The same shape shows up in real code, not just this synthetic example — e.g. an unannotated `functools.singledispatch` overload's own `return int(value)` for a `value: str` argument, found while dogfooding this check against a real third-party project, where the recheck couldn't see any contract requiring the return type to stay `int` across every overload. This is a real gap beyond the structural-match case `permissive` is meant to cover (e.g. `list[str]` satisfying `Iterable[str]`), where the argument's type is at least genuinely compatible with what's expected. Properly closing it would mean giving the hover gate its own real type-compatibility check between the argument and what the constructor produces, which is the same subtype/protocol-matching engine this whole architecture exists to avoid reimplementing — left as a known, opt-in risk of `permissive` mode specifically, the same way its four mutable constructors' own aliasing risk already is. Since this shape recurred across every real project dogfooded against this check (also a plain `dict` compared via `==` in a third project's own test suite), the reported message no longer claims "the argument is already `{constructor}`'s type" for this case specifically — `confidence.is_exact_match()` distinguishes a genuine type match from one this gap let through, and the message says so plainly instead of asserting something false. The same gap also shows up with no "sink" at all, weak or otherwise: a value returned from an unannotated function or lambda, with no caller in view that constrains its type either way (e.g. `lambda: bytes([an_int])`, found in a fourth project's own test suite, where nothing downstream ever checks that the lambda's return value stays `bytes`) — there's nothing for the recheck to diff against, so the wrap looks exactly as redundant as if the constructor genuinely didn't matter.
- **Superseded by ADR-0041**: the persistent session's compatibility controls run in a temporary directory under its workspace root because the serving `ty` session does not reliably analyse files outside that root. The temporary controls are closed before a failed session is closed and are removed by `TemporaryDirectory`; their prefix is ignored for interrupted-process cleanup.
- **Superseded by ADR-0041**: this check used to only ever examine the files pre-commit/prek/its own CLI invocation actually hands it in a given run — never the whole repository — so its own headline scenario (a redundant conversion at a call site, where the parameter's own type lives in a _different_ file) was only caught when both files were examined in the same run. A persistent, cross-invocation daemon (ADR-0041, closing issue [#109](https://github.com/alessio-locatelli/ruff-extra-rules/issues/109)) now closes this gap once the daemon has seen both files at least once; see that ADR for the current behavior and its own remaining accepted limitations.
