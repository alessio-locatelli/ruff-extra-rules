# redundant-type-conversion (TRI006): `ty`-driven detection over LSP

## Context

A builtin type-conversion call — `int(x)`, `list(x)`, and similar — is sometimes a no-op given the real, statically-known type of `x`. The only existing tooling that catches any part of this (pyrefly's `unnecessary-type-conversion`) only catches the trivial same-scope case, only for scalar builtins, and misses the more valuable cross-file call-site case entirely (confirmed empirically, not assumed — see the tool comparison below). Catching the cross-file case needs real, resolved type information; a local AST-only heuristic would mean re-implementing a subtyping/assignability engine, which this project's own architecture principles rule out as a maintenance burden and a correctness risk versus delegating to a real type checker.

## Tool selection

`ty`, `pyrefly`, `pyright`, and `mypy`/`dmypy` were measured against this repo's own size for query capability, latency, and daemon requirements. Full method and figures: `docs/audits/type-checker-selection-for-redundant-type-conversion.md`.

`ty` was chosen: fastest in every measurement taken (fresh-CLI and fresh-LSP alike), the cheapest recheck-cycle cost of the four, and the only one needing no daemon-lifecycle engineering to clear this project's existing performance budget (<1s best case, <3s worst case). Its main carried risk — explicitly pre-1.0, "no stable API, breaking changes possible between any two versions" per its own docs — is mitigated by the self-test below rather than assumed away.

## Decision

### Invocation

One `ty server` LSP session is kept alive for a whole hook invocation (not spawned per file or per query), driven by a hand-rolled, standard-library-only JSON-RPC client (`pre_commit_hooks._lsp`) — no third-party LSP client dependency, matching `docs/adding-a-check.md`'s "standard library only" rule for every check. The session is created lazily, on the first file this check actually examines, not at CLI startup — a run with nothing for this check to look at never pays `ty`'s startup cost.

### Detection method

Hover cheaply narrows which candidates are even worth the more expensive step; a synthetic in-memory rewrite (removing the wrapping conversion) plus a diagnostic recheck decides actual redundancy, by diffing "before" and "after" diagnostics rather than requiring either snapshot to be literally empty — an unrelated diagnostic present in both is not a signal either way. This drives `ty`'s own real assignability engine instead of reimplementing subtyping/protocol-satisfaction logic locally, which is what lets the same mechanism catch both the trivial same-scope case and the harder cross-file call-site case uniformly.

Detection is scoped to a call whose entire syntax — constructor name through closing paren — sits on one physical line. The rewrite splices out just the wrapping call syntax on that line; restricting this to single-line calls guarantees every other line's numbering stays intact, which the diagnostic diff depends on to mean anything. A multi-line-wrapped call is left out of this check's coverage rather than risking a wrong verdict from a shifted line number.

### Confidence tiering

`--redundant-type-conversion-level={conservative,permissive}` (default `conservative`) controls two independent axes:

- **Which constructors are candidates at all.** `conservative` considers only the seven whose result can never alias or share mutable state with their argument (`str`/`int`/`float`/`bool`/`bytes`/`frozenset`/`tuple`). `permissive` also considers the four copy-producing constructors (`list`/`dict`/`set`/`bytearray`) — the type checker's assignability recheck can confirm type-redundancy for these too, but can't distinguish that from a genuine aliasing/mutation-safety change (a copy becoming a shared reference), so this is an explicit, opt-in trade-off rather than a default-on one.
- **How strictly the hover pre-filter accepts a candidate before paying for the recheck.** `conservative` requires an exact match between the argument's own inferred type and what the constructor would produce — including a flow-narrowed `Literal[...]` of the same scalar (`ty` reports a variable's narrowed value at a given point, not just its wider declared annotation), matched by the literal's own textual spelling rather than runtime subtyping so that `bool`/`int` — a real subtype relationship that would otherwise let `int(some_bool)` slip through as if it were a no-op — are never conflated. `permissive` accepts any resolved, non-`Any` type, which is what lets a structural/protocol-satisfying match (e.g. `list[str]` satisfying an `Iterable[str]` parameter) through to the recheck — hover alone cannot decide that shape (see the audit's "Hover alone is not enough" finding), so `permissive` simply defers to the recheck's own verdict instead of pre-filtering on it.

### Suppression

A candidate on a line already carrying `# pytriage: ignore=TRI006`, or a third-party type-suppression comment (`# type: ignore`, `# pyright: ignore`, `# ty: ignore`), is always skipped outright, at either confidence level, by inspecting the target file's own source — never by trusting `ty`'s own diagnostics to already reflect the suppression. The synthetic rewrite preserves line numbers, so a pre-existing suppression comment would otherwise keep masking the recheck's own signal after the conversion is stripped, misreporting a genuinely necessary conversion as redundant; this was confirmed as a real, reproducible failure mode during development, not a theoretical concern.

### Failure handling

`check()` can raise a new `CheckUnavailableError` (see `docs/adr/0034-cacheable-check-flag-and-always-rerun-orchestrator-split.md`'s sibling decision for the orchestrator-level handling this required) in two distinct cases, each with its own actionable message: `ty` isn't on `PATH` at all (install hint), or `ty` is present but fails this check's own behavioral self-test (version-mismatch hint, distinct from the install hint since the remediation differs). The self-test runs once per process, before the real session is ever handed out, using one redundant-case and one necessary-case fixture as positive/negative controls — because `ty`'s own versioning policy allows breaking changes to diagnostics between any two versions, the pinned dev-dependency floor documented for install purposes is not trusted alone at runtime.

### No autofix

This check is detect-only in this version. A wrong report costs a human a wasted look; a wrong _fix_ could silently change program behavior around aliasing/mutation for a copy-producing constructor, a risk not yet fully designed for. Autofix is deferred entirely.

## Consequences

- This check requires `ty` as a separately installed prerequisite (`uv tool install ty`, or a project's own dev dependency) — not bundled with `ruff-extra-rules`, not a runtime dependency. A user without it on `PATH` gets a loud, one-time, actionable failure instead of silent empty output.
- This check's own test suite is a hybrid: the bulk of its logic is unit-tested against recorded/fake session responses for speed and determinism; a small integration layer (`tests/test_redundant_type_conversion_integration.py`) runs against the real, pinned `ty` binary and shares one warm session across the whole test module, so a future `ty` version bump is automatically checked for recorded-fixture staleness on every CI run.
- Restricting detection to single-line-wrapped calls is a real, accepted coverage gap, not a soundness one — a multi-line-wrapped redundant conversion goes unreported rather than risking a false verdict.
- `ty`'s own pre-1.0 status remains the primary long-term risk this decision carries; the self-test is this check's own mitigation, not a guarantee that every future `ty` release stays compatible without a code change.
- **Accepted limitation, not fixed**: hover reports an expression's _static_ type, which for a value annotated (or widened to) exactly `int`/`str`/`float`/`bytes`/`tuple`/`frozenset` also covers every runtime subclass of that type per Liskov substitution — a value statically typed `int` that's actually a custom `IntSubclass` instance at runtime looks identical to hover. `int(such_a_value)` genuinely normalizes it to a plain `int`, which removing the call would not. This is inherent to any purely static-type-based redundancy check (the same gap exists in pyrefly's own narrower `unnecessary-type-conversion` rule) — closing it would mean either reimplementing local subtype-flow tracking (the exact re-implementation this whole architecture exists to avoid) or restricting `conservative` mode to `Literal[...]` hovers only, which would gut it down to a small fraction of its current, useful cases. Left as a known, narrow trade-off: it requires a codebase to both subclass an immutable builtin and rely on a conversion's normalizing side effect, an unusual combination in practice.
- **Accepted limitation, not fixed**: the compatibility self-test (see "Failure handling" above) runs its two control fixtures in an isolated scratch directory with no `ty` config of its own, while the real session opens files under the consuming project's own working directory and therefore inherits _its_ `ty` configuration. A project that explicitly configures `ty` to suppress or downgrade a diagnostic this check's own recheck step depends on (e.g. disabling `invalid-argument-type` outright) would pass the self-test — which never sees that configuration — while the real session's recheck silently stops seeing the diagnostics that make a necessary conversion look necessary, misreporting it as redundant. Running the self-test's own control files inside the real project tree instead (so `ty`'s config discovery picks up the same configuration) was considered and rejected here: it would mean writing throwaway files into a user's real working directory during a lazy, lock-guarded singleton initialization, with its own new cleanup and cross-process-race concerns, to defend against a configuration choice that already affects every other consumer of that project's own `ty` diagnostics equally — not something specific to this check.
- **Accepted limitation, not fixed, tracked separately**: this check (like every other check in this hook) only ever examines the files pre-commit/prek/its own CLI invocation actually hands it — never the whole repository. Its own headline scenario (a redundant conversion at a call site, where the parameter's own type lives in a _different_ file) is therefore only caught when both the call-site file and the file whose signature changed are examined in the same run — either because a single commit happens to touch both, or because the check is run over the whole tree (`pre-commit run --all-files`, CI, or an explicit full-tree invocation), not on an ordinary incremental commit that only touches the changed file. This mirrors a gap the original research (`docs/audits/type-checker-selection-for-redundant-type-conversion.md`, "Conflict with this repo's existing per-file cache contract") already flagged and explicitly deferred; making this check's own cross-file awareness survive a commit that only touches one side of the relationship would need a persistent cross-file dependency graph (which file imports which, invalidated and re-walked as imports change) that neither this check nor `CheckOrchestrator` has any machinery for today — a materially larger, separate undertaking, tracked as its own follow-up (issue [#109](https://github.com/alessio-locatelli/ruff-extra-rules/issues/109)) rather than folded into this implementation.
