# A persistent `ty server` daemon closes TRI006's cross-file reanalysis gap

## Context

`redundant-type-conversion` (TRI006) only ever examines the files pre-commit/prek/its own CLI invocation passes to it in a given run (see `docs/adding-a-check.md`'s "Incremental-analysis limitations" and ADR-0035's own accepted-limitation note). Its headline scenario — a redundant conversion at a call site whose parameter type is declared in a different file — is therefore only caught when both files are examined in the same run, not on an ordinary commit that only touches the file whose signature changed. Tracked as issue [#109](https://github.com/alessio-locatelli/ruff-extra-rules/issues/109), which listed three undecided candidate directions without picking one.

Issue [#123](https://github.com/alessio-locatelli/ruff-extra-rules/issues/123) recorded a spike confirming that `ty server` already tracks the real cross-file dependency graph internally: telling it a file changed (`workspace/didChangeWatchedFiles`), even for a file it was never asked to open, makes it proactively push (`textDocument/publishDiagnostics`) updated diagnostics for whichever other, already-open file depends on it — without this project ever building or maintaining that graph itself. That spike was recorded as research only, explicitly out of scope for its own implementation, to give a later design session a validated starting point.

## Considered Options

- **A self-maintained cross-file import-dependency graph** (#109's first candidate): rejected. Resolving Python's own dynamic import machinery correctly (conditional imports, `importlib`, re-exports, `TYPE_CHECKING`-only imports that still affect declared types) to build and invalidate this graph is exactly the risk ADR-0034 already rejected for the narrower job of a cache key, just scoped up to a whole graph instead of one file's own imports.
- **Scoping cross-file awareness to something coarser** (#109's second candidate) with no further mechanism: rejected as insufficiently general on its own — it would still need some concrete trigger, and the daemon approach below already provides a coarser, working one (see "Consequences").
- **Documentation only**: recommend running the hook over the full tree periodically (`pre-commit run --all-files`, CI) rather than changing any code (#109's third candidate): rejected as a replacement for closing the gap, though nothing here removes it as a useful complementary recommendation for a repository that can't or won't run the daemon.
- **A persistent `ty server` daemon that reuses `ty`'s own confirmed cross-file push behavior** (#123's spike): adopted.

## Decision

### Daemon lifecycle

One daemon process per canonical Git repository root is spawned on demand behind a Unix domain socket at `.cache/pre_commit_hooks/tri006-daemon.sock`. The root is the nearest `.git` ancestor of the resolved current directory, so subdirectory invocations and equivalent path aliases reuse the same socket, pidfile, and persisted state; outside a Git worktree, the resolved current directory is used. Spawning is guarded by the same exclusive-lock primitive `CacheManager` already uses for its own per-file cache writes, so two concurrent hook invocations in the same repository never race to start two competing daemons. On a platform where that lock primitive itself isn't available, spawning is refused outright (falling back to a local session below) rather than proceeding unguarded.

A client that can't get an answer within a short connect timeout can't tell "no daemon running" apart from "a live daemon that's simply too busy to accept and hand off this one connection yet" from the socket alone — connections are handled concurrently (see below), so this is rare, but a large enough simultaneous burst (e.g. every pre-commit/prek worker process connecting at once) can still exceed it. A small pidfile alongside the socket resolves that ambiguity: a client that finds a live process recorded there waits for it to catch up instead of spawning a competing daemon, which would otherwise unlink the first one's socket out from under it (and could later have its own socket unlinked the same way once the first one finally exits).

On connect, a handshake compares the connecting client's own `ty --version` against the version the daemon was started with; a mismatch (e.g. the user upgraded `ty` since the daemon started) makes the daemon shut itself down and the client spawn a fresh one. This case is distinguished from an ordinary busy daemon rather than folded into it: a client told explicitly that its handshake was rejected for this reason spawns a replacement immediately instead of waiting out the same busy-daemon budget it would for one that's merely still serving someone else, since a departing daemon was never going to answer either way. The daemon also exits on its own after an idle period with no connected client, rather than through any finer-grained per-file eviction — a coarse, easy-to-reason-about bound on its own resource growth over fine-grained precision, the same trade-off #109 itself already suggested as a fallback direction.

Because a replacement can be spawned before the daemon it's replacing has actually finished exiting, the outgoing daemon's own cleanup only ever removes the socket and pidfile if the pidfile still names its own process: unlink() acts on whatever currently occupies a shared path, not on whoever created it, so an unconditional cleanup here could otherwise delete a freshly started replacement's live files instead of its own already-defunct ones. A replacement claims that pidfile identity before ever binding its own socket, not after, so this ownership check can never observe a live socket still credited to a process that's already gone. A client that already learned a daemon is departing from an earlier attempt (rather than merely busy) never re-treats it as busy later just because a subsequent attempt can no longer observe that same rejection directly — for instance once the departing daemon's own socket is already gone.

A crashed daemon's own leftover socket is also cleaned up by an ordinary client, not only by a future spawn: once independently confirmed dead (no live process behind its pidfile), leaving it in place would otherwise widen this check's own prefilter (`get_prefilter_pattern()`, see below) indefinitely in a repository where no later, candidate-containing commit happens to run `connect()` to notice and replace it.

The candidate-less notification path (see below) waits out the same busy-daemon budget as an ordinary connect rather than treating a confirmed-alive-but-busy daemon as unreachable. It caches a successful connection and memoizes only terminal failures, such as an unavailable local `ty`; missing, busy, timed-out, stale, or departing daemons remain retryable. A bounded retry interval avoids probing for every file while allowing a later file in the same run to resend its disk-change notification after a transient failure. The path still never spawns a daemon itself.

Connections are accepted and handled concurrently, one worker thread per connection, rather than one at a time: pre-commit/prek run this hook's own file-batches across several parallel worker processes, each opening its own connection, so serving them one at a time would force work that used to run in parallel (each worker's own file batch) through a single connection instead. Candidate analysis holds the lock around its complete baseline, synthetic-rewrite, diagnostic-comparison, and final re-sync transaction; other session operations hold it for their own call. `_lsp.LSPClient` is documented as not thread-safe for concurrent `request()`/`notify()` calls, but the handshake and message framing around it don't touch `ty` at all, so accepting, handshaking, and reading/writing frames for many connections at once is safe without it. A version mismatch or an explicit shutdown request signals the accept loop instead of ending it directly, since it's detected on a worker thread, not the accept loop's own; the accept loop itself polls its own `accept()` briefly rather than for the full idle timeout, so it notices that signal promptly, stops accepting new connections, and lets every already-accepted, already-handshake-matched connection finish its own in-flight work before the daemon's process actually ends.

A connection that's accepted but then stalls mid-request — never completing a message — is bounded by its own per-connection timeout, separate from the idle-accept timeout above: without one, its own worker thread (and the connection's socket) would leak indefinitely, though — unlike before connections were handled concurrently — no longer at the cost of blocking any other, already-accepted connection.

A client that disconnects abruptly mid-request (an interrupted hook process, a truncated frame, a reset connection) or after this daemon has already committed to answering it (a broken pipe on the reply) is treated the same way: the one connection's own worker thread drops it and ends cleanly, without disturbing any other in-flight connection. A malformed request (a missing or wrong-typed field) is treated the same way rather than escaping as a raw exception: client and daemon are always the same, handshake-matched code, so this should never happen in practice, but an uncaught exception here would otherwise surface as a noisy, unhandled-thread-exception traceback for what's really just an ordinary client-side failure.

The client side of this same connection also carries a bounded timeout once past its own initial handshake, not an unbounded wait: a daemon that's genuinely wedged (not merely slow on one `ty` request, which the daemon's own internal request timeout already resolves into an ordinary error response) would otherwise hang the client invocation forever, with nothing to ever fall back to a local session.

A client that can't reach or spawn a working daemon for an operational reason (no socket support in the environment, a spawn failure unrelated to `ty` itself) falls back to today's private, per-invocation `ty server` session — the same session this check has always used, just without cross-file persistence. `ty` itself being missing or failing its own compatibility self-test is a different, non-fallback-worthy failure (`CheckUnavailableError`, unchanged from ADR-0035): falling back to a local session in that case would only reproduce the identical failure a second time.

### Reusing `ty`'s own dependency tracking instead of building one

The daemon keeps every file it has ever examined open in its one long-lived `ty server` session, rather than closing each one after every check the way today's per-invocation session does — this is what lets a dependent file from an earlier, separate commit still be around to receive `ty`'s own proactive push when a later commit changes something it depends on.

A file kept open this way must be re-synced to its real, current on-disk content before being left open, not simply left wherever its own redundancy analysis last put it: this check's own detection method (ADR-0035) temporarily rewrites a file's in-memory content per candidate to test redundancy by diffing diagnostics, and today's design discards that document immediately afterward specifically so the exact content left open never matters. A session built to keep files open instead must push the file's real content back first, or a later request against it — on a separate, future invocation — would start from `ty`'s memory of the last synthetic rewrite rather than the file's real state. This is the one piece of this decision not already flagged by either issue; it falls directly out of keeping a session alive across invocations instead of discarding it after each one.

Confirmed empirically against real `ty`, both of the following are required every time a tracked file changes, regardless of whether it was already open: an ordinary edit notification alone (without also telling `ty` the file changed on disk) never triggers the proactive push for dependents; and, since that push is asynchronous relative to the notification that triggers it, nothing here waits for it to actually arrive unless something forces a round trip afterward. A synchronous request against any other already-tracked file, sent immediately after, is that forcing function — `ty` answers requests in the order it receives them, so its response means `ty` has already finished acting on the notification sent just before.

`CheckOrchestrator` gains one new, optional extension point on `ASTCheck`: a check may report additional files it privately knows need re-examination as a side effect of state only it tracks, merged into the same run's report exactly as if pre-commit/prek had passed those files directly. TRI006 is the only check implementing this today: it asks its own session which previously-tracked files just received a push notification.

Draining happens right after each file's own examination, excluding only that one file — not every file this run was ever given up front. Two files changed by the same commit, where the dependent happens to be examined before its own dependency later in that same run, is the common case this has to get right, not an edge case: excluding the whole input set from the very start would make the dependent's own earlier result permanently stick, even after its dependency's own examination reveals it stale, silently reopening the exact gap this decision exists to close for exactly the files most likely to change together. Because a change can itself ripple further (`a.py` affecting `b.py` affecting `c.py`), draining repeats until a fixed point or a small iteration cap, rather than either stopping after one pass or walking the whole dependency graph unbounded.

Because a drained file can itself be one of this run's own direct inputs, re-checking it replaces only that one check's own prior result for it rather than appending to it, and reports it under the same key its own direct examination already used (its original, possibly-relative spelling) rather than a second, separately-resolved one — otherwise the same file's own violations could double up, a result that's now clean could still show its own stale, no-longer-true report, and the same file could appear twice under two different spellings in the same run's report.

A drained file can also be one of a _different_, concurrently running pre-commit/prek worker process's own direct input: this hook's own file-batches run across several parallel worker processes (up to CPU count), each a separate OS process with no visibility into the others. `redundant-type-conversion` itself never writes (`fixable=False` on every violation it reports, `fix()` a no-op) — draining it alone can never race a write today — but `CheckOrchestrator._check_file()` still holds a per-file advisory lock (`_fix_lock_path`, keyed by the file's own resolved path, reusing the same `_filelock` primitive as `CacheManager` and this daemon's own spawn lock) around every fix-mode file's own read-check-fix cycle regardless, direct input or drained candidate alike. This is a general safeguard, not one specific to this decision: `atomic_write_text()`'s own `tempfile.mkstemp()` choice already anticipated two hook processes fixing the same file at once (its own unique name avoids the two colliding on the same sibling `.tmp` path), which this lock extends from "don't collide" to "don't silently lose one fix to the other" — whichever `atomic_write_text()` call would otherwise land last, discarding an already-applied fix. It also stands ready for the day `redundant-type-conversion` gains its own `--fix` support: draining it would then create exactly the two-workers-same-file scenario `docs/behavioral_contract.md`'s ch. 16 ("MUST NOT allow two workers to apply competing modifications to the same file without coordination") describes, a gap a prior audit (`docs/audits/0007`) had judged not applicable before this decision's own cross-file drain existed at all. A worker that can't acquire this lock within a bounded timeout treats the file as unprocessable for this run rather than proceeding unlocked — any violation is still there to catch once the other worker finishes, on this run or the next.

A pure signature change — #109's own example, widening a parameter from `list[int]` to `Iterable[int]` — usually has no redundant-conversion candidate of its own in the file being edited: this check's existing lazy-start optimization (ADR-0035) only ever touches a session at all once a file has a real, non-suppressed candidate. Left alone, such a file would never tell even an already-running daemon that it changed, silently reopening the exact gap this decision exists to close. This check's own candidate-less path now also tells an _already-connected_ session about the change, cheaply, without ever spawning one on its own — a repository that has never had a real candidate anywhere still never pays `ty`'s startup cost just because an unrelated file changed.

This check's own prefilter (a `git grep` fast path skipping any file that can't contain a redundant-conversion candidate at all, before it's even parsed) has the same blind spot one level earlier: a signature-only change never matches it either, so the file would never even reach `check()` in the first place, let alone this decision's own candidate-less notification path. The prefilter itself now widens to "check every file" for the whole run once a daemon might already be running for this repository (a plain, non-connecting existence check against its own socket path) — otherwise it stays exactly as narrow as before. A repository that has never used this daemon pays nothing extra; one that has now pays a full per-file AST walk (not a `ty` round trip) on every file, every run, in exchange for the daemon actually having a chance to hear about every change.

A daemon's own persistence is scoped strictly to the repository root it was spawned for: a file outside that root is always closed again once this run's own analysis of it finishes, in either mode, never kept open or reported by a later drain. The daemon's own identity (its socket/pidfile path) is keyed only by the current working directory a client connects from, not by which files it's actually asked to examine — a direct CLI invocation naming a path elsewhere on disk (rather than pre-commit/prek's own file list, always within the repository being committed) would otherwise get adopted into that same long-lived session, and could resurface in a later, unrelated run against that repository once `ty`'s own cross-file push happened to touch it again.

## Consequences

- TRI006's headline cross-file scenario (#109) is now caught on the commit that actually creates it, not only when a later commit happens to also touch the caller or during an explicit full-tree run — provided the daemon has been running long enough to have already seen both files at least once.
- A brand-new daemon — first use in a repository, or immediately after a version-bump restart — starts with no cross-file awareness at all; it only accumulates it as commits pass files through it over time. This decision does not retroactively index a whole repository's dependency graph on first use.
- The daemon's own memory footprint grows with the number of distinct files it has seen since its last restart, bounded only by the idle-timeout restart, not by any explicit per-file cap — an accepted, coarse trade-off over building fine-grained eviction.
- Connections are handled concurrently (one worker thread each), but candidate-analysis transactions and other calls into the shared `ty` session are serialized behind a lock: throughput for many overlapping invocations is bounded by `ty`'s own request-processing speed either way, but a connection no longer has to wait for an unrelated, already-connected client's own entire file batch to finish before its own handshake is even answered.
- The pidfile-based liveness check inherits the one inherent risk any PID-based check carries: a crashed daemon's own PID being reused by an unrelated process before anything notices is possible, if rare, and isn't defended against further here.
- Once a daemon exists for a repository, this check's own prefilter no longer skips any file — every file this check is handed pays a full AST walk (`find_candidates()`) every run, not just ones matching its candidate-name pattern. This is a real, permanent cost increase for that repository specifically (never a `ty` round trip, only the AST walk), accepted in exchange for the daemon actually being told about every change, not only ones that happen to contain a redundant-conversion candidate of their own.
- This remains dependent on `ty`'s own pre-1.0, undocumented cross-file push behavior (already an acknowledged risk in ADR-0035) continuing to hold across versions and across a real multi-commit workflow — neither is guaranteed by `ty`'s own compatibility policy, only empirically confirmed once, in #123's own spike.
- No independent filesystem watching is added: the daemon only learns a file changed when some future commit's own hook invocation hands that file to it, exactly like every other check in this repository. A `git checkout` or rebase that moves files around without ever running this hook against them is not covered — left as an open question exactly as #109 itself left it, not decided further here.
- Every fix-mode file, not only a drained one, now pays a per-file lock acquisition (an uncontended `flock` — negligible) before its own check-and-fix cycle. This isn't specific to `redundant-type-conversion`'s own drain mechanism (which never writes today) — it's a general safeguard already implied by `atomic_write_text()`'s own pre-existing `mkstemp()` uniqueness choice, and it's ready in advance for whichever comes first: `redundant-type-conversion` itself gaining `--fix` support, or a future check implementing `drain_cross_file_candidates()` while also being fixable.
