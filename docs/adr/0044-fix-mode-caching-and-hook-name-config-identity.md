# Fix mode reads and writes the cache; `hook_name` carries check-set/config identity

## Context

ADR-0043 documented, as a known limitation rather than a bug, that `--fix` bypasses `CheckOrchestrator`'s per-file cache entirely — reading nothing, writing nothing — for every file, every run, regardless of whether that file needs fixing. It recorded one unimplemented option: trust a cache hit for the cacheable group when it's empty, still run the always-rerun group fresh, and fall back to a real check-and-fix pass only when either group's own result turns up a violation (a cached diagnostic never carries `fix_data`, so a hit that shows a violation can't be used to fix it).

Implementing that option surfaced a second, unrelated problem in `CheckOrchestrator._generate_cache_key()`: it folded four things into one `cache_version` string — the enabled cacheable checks' IDs, their own per-check config, this package's own source-tree hash, and the interpreter's version — all gating a single per-file cache blob stored under one hardcoded `hook_name="ruff-extra-rules"`. `CacheManager.set_cached_result()` resets the _entire_ blob on a version mismatch, not just the mismatched entry. Two `CheckOrchestrator`s sharing that hook_name but differing in cacheable-check config (e.g. this repo's own `local-ruff-extra-rules-default` and `local-ruff-extra-rules-aggressive` hooks, which run back-to-back against the identical file set with different `--meaningless-vars-level`/`--redundant-assignment-level`) would perpetually overwrite each other's cache entry. This collision already existed for check-only mode too; it was simply never exercised, because fix mode never touched the cache at all, and this repo's own hooks never run check-only.

Read-only caching in fix mode, on its own, would never actually help this repo's own hooks, or any pure `--fix`-only workflow: fix mode has never written to the cache either, so nothing would populate it in the first place. Delivering real value required also enabling cache writes in fix mode — which immediately activates the collision above on this repo's own commits.

## Considered Options

- **Read-only fix-mode caching, deferring the collision to a follow-up**: rejected. It ships a change that provably never fires for this repo's own `--fix`-only hooks, or for any consumer whose workflow is `--fix`-only, since nothing would ever populate a cache that only reads.
- **Read+write fix-mode caching without addressing the collision**: rejected. Enabling writes without fixing it would make `local-ruff-extra-rules-default` and `local-ruff-extra-rules-aggressive` thrash each other's cache entry on every commit — added cache I/O with a permanent 0% hit rate for this repo's own two most common hooks, worse than the pre-existing status quo.
- **Fix the collision inside `CacheManager` by versioning each `hook_results` entry independently, instead of one version per blob**: rejected. `CheckOrchestrator` only ever used one hardcoded `hook_name` regardless of config, so two differently-configured orchestrators would still target the same entry under this option — it changes what gets overwritten, not whether it collides.
- **Fold check-IDs and their fingerprints into `hook_name`, narrow `cache_version` to source-tree hash plus interpreter version, and enable fix-mode read+write together**: adopted (below).

## Decision

`CheckOrchestrator` now builds two separate identities instead of one combined key: `_generate_hook_name()` (a short hash of the enabled cacheable checks' IDs and their own config) and `_generate_cache_version()` (the source-tree hash and interpreter major.minor, unchanged from ADR-0005 except for what moved out). `hook_name` answers "which configuration produced this entry"; `cache_version` answers "can any entry in this file's cache blob be trusted at all." Two orchestrators with different cacheable-check config now get independent, coexisting entries in the same per-file blob, instead of overwriting one hardcoded name.

`_process_single_file()` reads the cacheable group's cache entry in both check and fix mode. In fix mode, the hit is trusted only when it reports zero violations — a hit showing a violation still falls through to a full check-and-fix pass, since `fix_data` is never cached. When the hit is empty and no always-rerun check applies to the file, the file is never read or parsed at all. When always-rerun checks do apply, only those run fresh (the same branch check-only mode already used); if they turn up something fixable, it gets fixed without re-running the already-confirmed-clean cacheable group.

Fix mode also writes to the cache now, at the same point check mode already did, with three restrictions specific to fixing:

- A violation marked fixed is excluded from what's cached (it no longer exists in the file).
- An entire check_id is excluded if any of its violations hit a rejected, errored, or aborted outcome this run — mirroring `_refresh_stale_positions`'s existing precedent of leaving that check_id's other, still-open positions unrefreshed in the same situation, since caching a check_id whose positions aren't verified current would violate the requirement that a cache hit and a fresh check produce equivalent results.
- Nothing in the cacheable group is cached at all for a run where any check's own fix actually changed the file's content (`CheckOrchestrator._fix_changed_file`, set by `_apply_fixes`). A check with zero violations is never re-verified against the file's final content once some _other_ check's fix has run — `_apply_fixes`'s own per-check loop only recomputes a check_id already present in `violations`, and `_refresh_stale_positions()` only revisits a check_id that already has entries there — so a check that found nothing at the start of the run is invisible to both, and its "found nothing" result can no longer be trusted for the file's post-fix content. A file that actually gets fixed converges to a cached hit on its first _unchanged_ run afterward instead of the same run.

The same reasoning applies to the read side: a clean cacheable-group cache hit, combined with an always-rerun check that turns out to have something to fix, is trustworthy only if that fix didn't itself change the file — an always-rerun check's own fix can invalidate whatever made the cacheable group clean, the same way one cacheable check's fix can invalidate a zero-violation sibling. `_process_single_file()` checks `_fix_changed_file` after running the always-rerun group; when it's set, it re-verifies (and fixes, if needed) just the cacheable group fresh, merging in the always-rerun group's own already-computed result rather than discarding it. Re-running the always-rerun group a second time, as a naive "fall back to a full recompute" would, silently loses that group's own `[FIXED]` outcome: a violation already resolved is gone from the file, so a second `check()` call no longer sees it to report on at all — cache hits and misses must produce equivalent results (ch. 9), which requires preserving an outcome from earlier in the same run just as much as it requires not serving one that's gone stale.

Separately, allowing several `hook_name`s to share one file's cache blob (the change above) means `CacheManager.set_cached_result()` can no longer treat a version match as license to leave every _other_ hook_name's entry untouched: if the file's content changed since the blob was last written — detectable from the content hash `set_cached_result()` already computes for its own write — every existing `hook_results` entry was computed against that older content and must be dropped, not just the one this call is about to overwrite. Without this, one hook_name's write could silently keep a content-addressed but no-longer-accurate sibling entry alive under the blob's newly-updated file identity.

A residual gap remains, structurally the same one ADR-0042 already accepted for the source-file write itself: between `_check_file()` returning (and releasing its fix lock) and `_cache_violations()`'s own read of the file to compute what to write, an external edit could land. `set_cached_result()` would then hash the new content while caching diagnostics computed from the old one. This is not new to fix mode — check-only mode's cache write has carried the same unlocked window since ADR-0005 — and closing it further is out of scope here for the same reason ADR-0042 gave for not closing its own analogous gap: no daemon, lock, or other mechanism beyond what the existing write pattern already provides.

ADR-0043 is superseded by this decision and is annotated rather than rewritten, per this project's existing convention for a later ADR revisiting an earlier one (see ADR-0042's own consequences section for precedent). ADR-0005 (the original four-factor `cache_version`) and ADR-0034 (which described a "shared cache-version fingerprint" derived from the cacheable group) are annotated the same way, since this decision narrows what each originally specified.

## Consequences

- `--fix` gets the same warm-cache speedup a check-only run already gets, for a file with nothing to fix — see the commit introducing this ADR for cold/warm measurements on both the direct CLI and `prek run local-ruff-extra-rules-default --all-files`, superseding ADR-0043's own numbers.
- A file that actually needs fixing costs one extra, otherwise-avoidable full recompute on the run immediately after it's fixed (nothing from that run is cached), before converging to normal cache-hit behavior once it stops changing.
- Every distinct cacheable-check configuration ever run against a file keeps its own permanent entry in that file's cache blob, rather than evicting whichever configuration ran last. This is bounded in practice by how many distinct configurations a repository actually runs — small and developer-controlled, not something that grows with commits or file count (this repo has exactly two: default, aggressive) — but it is not literally zero growth, and no eviction mechanism was added.
- The first run under this change invalidates every existing on-disk cache entry once, since an old entry still carries the previous four-factor `cache_version` format — the same one-time cost every prior cache-key format change already carried (ADR-0005, ADR-0014).
- No change to `--fix`'s own correctness: ADR-0042's concurrent-modification handling and ADR-0041's per-file fix lock are unaffected, since neither depends on whether the cache was consulted first.
- `docs/faq.md`'s "`--fix` doesn't use the cache" entry is removed rather than rewritten: once `--fix` behaves the way any caching tool is expected to by default, there's no longer a real question left to answer.
