# A file no enabled check's prefilter matches is never parsed, so a syntax error in it goes unreported by design

## Context

`CheckOrchestrator._checks_by_file()` asks each enabled check's `get_prefilter_pattern()` whether a file can possibly contain that check's violation before paying to read and parse it. When a file matches no enabled check's pattern and `per-file-ignores` (ADR-0049) didn't switch anything off for it either, `applicable` and `ignored` are both empty and the file gets no entry in `checks_by_file` at all (`_orchestrator.py`'s `if applicable or ignored:` gate). Such a file never reaches `_check_file()`, so it is never opened, parsed, or added to `self.unprocessable_files` — the run reports nothing for it and exits `0`.

Filed as [issue #158](https://github.com/alessio-locatelli/ruff-extra-rules/issues/158), reproduced with `--select=meaningless-vars` against a file whose only content doesn't match `meaningless-vars`' own prefilter pattern and is missing a closing paren. The same file given content that does match a prefilter pattern is read, fails to parse, and is correctly reported via `self.unprocessable_files` (ADR-0011) with exit `1`. Both published hooks (`ruff-extra-rules`, `ruff-extra-rules-ty`) are unaffected at their default selection, because `excessive-blank-lines` returns `None` from `get_prefilter_pattern()` and so is asked about, and keeps an entry for, every file — the gap only surfaces under a narrower `--select`.

`docs/behavioral_contract.md` ch. 4 ("MUST NOT silently skip a file because parsing failed") and ch. 13 ("MUST NOT silently skip inaccessible files") read as if this should be fixed. ADR-0011 already established the actual precondition those chapters were audited against: "this project's precondition (every file already passed `check-ast`/ruff in the same pre-commit run) still holds, and invalid-syntax handling stays a catch-log-skip fallback rather than a recovery path." That precondition already holds in this repo's own `.pre-commit-config.yaml`, where `check-ast` and `ruff-check` run in the same invocation as the local `ruff-extra-rules*` hooks — a syntax error is reported by `check-ast` and blocks the commit regardless of what any later hook in that same run does or doesn't say about the same file.

## Decision

Accepted as out of scope, not fixed. A file no enabled check's own prefilter matches is never read or parsed, and a syntax error in such a file produces no diagnostic from this tool. This tool documents (README, FAQ) that it must run alongside `check-ast`/`ruff check` in the same pre-commit/prek invocation, and relies on one of those to report a syntax error — matching the precondition ADR-0011 already assumed, now made an explicit, documented scope boundary rather than an implicit one a narrower `--select` could quietly fall outside of.

Forcing every enabled check's prefilter-rejected file through a full read-and-parse just to catch this case would mean parsing files specifically because they _can't_ contain anything any enabled check is looking for — reintroducing the exact per-file parse cost the prefilter exists to avoid (`docs/adr/0013-behavioral-contract-audit-resource-timeouts-performance.md`), for a case the intended usage (this tool never run standalone, always paired with `check-ast`/`ruff`) already covers elsewhere.

This differs from the `per-file-ignores` case (ADR-0049), which is deliberately kept out of this exception: a file `per-file-ignores` emptied out was still explicitly named as input by the user or by pre-commit/prek's own file list, so `_checks_by_file()` keeps an (empty-`run`) entry for it and it still reaches `_check_file()`, still lands in `unprocessable_files` if unparseable, and still forces exit `1`. Only a file that no enabled check's prefilter would ever have looked at falls under this ADR.

## Considered Options

- **Parse every file regardless of prefilter match, purely to catch syntax errors**: rejected — reintroduces the full parse cost the prefilter is the whole point of avoiding (ADR-0013), for a case that requires either running this tool without `check-ast`/`ruff` in the same invocation (already against documented usage) or a `--select` narrow enough that every enabled check's prefilter misses the one file with the syntax error (a corner few real configurations hit).
- **Add a dedicated "does this file parse at all" prefilter that every check implicitly shares, independent of any check's own pattern**: rejected — this is a second cheap check with its own git-grep-vs-Python-scan cost for every file, every run, to protect against a failure mode this tool's documented precondition (paired with `check-ast`/`ruff`) already prevents from mattering in practice.
- **Document the scope boundary and require `check-ast`/`ruff` in the same run**: adopted (above) — zero runtime cost, matches this repo's own dogfooded `.pre-commit-config.yaml`, and formalizes what ADR-0011 already assumed rather than changing behavior.

## Consequences

- `_checks_by_file()`'s own docstring and its `if applicable or ignored:` gate now reference this ADR, so a future reader doesn't mistake the drop for an oversight the way issue #158 initially did.
- `main()`'s exit-code docstring (`_cli.py`) is corrected: exit `0` no longer claims "every requested file was read, parsed, and checked" — a file no enabled check's prefilter matched was never read or parsed at all, and still contributes to a `0` exit.
- README and the FAQ now state that a syntax error is out of scope for this tool and depend on `check-ast`/`ruff check` running in the same pre-commit/prek invocation to be reported. The FAQ's own "Running without prek/pre-commit" section — the one documented way to invoke this tool with no `check-ast`/`ruff` alongside it at all — cross-references that same guidance, so a standalone-CLI user isn't left assuming pre-commit's own protection still applies.
- A user who runs this tool's CLI standalone, bypassing `check-ast`/`ruff`, with a `--select` narrow enough that no enabled check's prefilter matches a syntactically invalid file, gets a clean, silent exit `0` for that file — an accepted limitation of the documented usage, not a bug to file again.
