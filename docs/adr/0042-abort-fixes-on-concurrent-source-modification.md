# Abort a fix when its source changed on disk since it was read

## Context

`atomic_write_text()` (`ast_checks/_base.py`) reads a file, computes a fix against that content, and writes the result back via temp-file-then-rename — with no check that the file on disk is still the version the fix was computed against. `docs/audits/0002-behavioral-contract-audit-fix-engine.md` found this gap against `docs/behavioral_contract.md` ch. 3 ("MUST NOT silently overwrite a newer version of a file created by another process") and judged it not worth closing: the only realistic actor was a human editing the same file in another program while `--fix` ran locally, "the same limitation essentially every linter with `--fix` has," and a real fix would need an mtime/hash compare-and-abort before the rename — disproportionate for a single-maintainer local hook with no parallel workers.

Issue [#137](https://github.com/alessio-locatelli/ruff-extra-rules/issues/137) revisits that call: the risk was accepted for a single local user without parallel workers, but this project is a formatter-adjacent tool other people's editors and CI run `--fix` under, where a silently discarded concurrent edit is a data-loss bug, not a tolerable edge case. This is distinct from `ADR-0041`'s per-file fix lock (`CheckOrchestrator._fix_lock_path`): that lock only serializes two processes that both go through this tool's own orchestrator (e.g. two overlapping pre-commit/prek worker batches); it cannot see an editor, or any other process, writing to the file directly.

## Considered Options

- **mtime/size staleness check**: reject the write if the file's `stat()` no longer matches what it was at read time. Rejected as the primary mechanism — cheap, but only as precise as the filesystem's timestamp resolution, and a same-size edit can leave `stat()` looking unchanged depending on what's compared. `expected_source` already needs to be read in full to compute the fix itself, so an exact comparison costs the same one extra read this project's own performance principle requires measuring, for a strictly more reliable answer.
- **A new `SourceIdentity` fingerprint (e.g. a digest) threaded through the `ASTCheck.fix()` protocol**: rejected. `fix()`'s `source: str` parameter already carries everything needed to answer "did the file change since this was read" — a fix's own computed output is derived from that same `source`. Adding a parallel identity value would duplicate what `source` already encodes, and forcing every `ASTCheck.fix()` implementation (five checks, ~90 direct test call sites) to accept and pass through a new required parameter for no additional accuracy over comparing against `source` itself was unjustified surface area for this decision.
- **Compare `expected_source` (the exact source each fix was computed against, encoded via the same `encoding` `atomic_write_text()` already receives) against a fresh read of the file's current on-disk bytes, inside `atomic_write_text()` itself**: adopted. Every write already flows through this one function (see its own docstring), so this is the one place a check can be enforced for every check's fix path without changing the `ASTCheck.fix()` protocol at all — only `atomic_write_text()` gained a required fourth parameter, `expected_source: str`. A check with a single write per `fix()` call passes the `source` it was handed; `validate_function_name`'s own multi-write `apply_fix()` (which re-reads the file itself between writes, since an earlier rename in the same batch can shift a later one's positions) passes its own fresh read instead — each call is responsible for the exact source its own edit was computed against, the same responsibility it already has for `encoding`.

## Decision

`atomic_write_text()` re-reads `path`'s real current bytes and compares them against `expected_source` encoded via `encoding`, immediately before the rename that commits the write (after the temp file is written, not before) — narrowing, as far as this write pattern allows, the window in which a concurrent change could land unnoticed. A mismatch raises `ConcurrentModificationError` and leaves `path` and its temp file exactly as `FixValidationError` already does: the temp file is created and populated, but the finally-cleanup still removes it, and the target is never renamed over.

Every check's `fix()` implementation follows the same split already established for `FixValidationError` (see `docs/adr/0010-fix-validation-before-write.md`): a single-write `fix()` lets `ConcurrentModificationError` propagate uncaught, and `CheckOrchestrator._apply_fixes` attributes the abort to every violation that check's own re-check just produced via the existing `mark_fix_aborted()`/`is_fix_aborted()` pair, mirroring `mark_fix_rejected()`. A multi-write `fix()` (`validate_function_name`) catches it around each individual write and marks only that violation, so a rename earlier in the same batch that already committed stays `[FIXED]` rather than being swept into the abort. Diagnostics report this outcome as `[FIX ABORTED]` with a hint directing the user to re-run `--fix`, distinct from `[FIX REJECTED]` (a bug in the fix's own output) and `[FIX FAILED]` (an environmental write failure) — re-running is the correct, and only necessary, recovery, since the fix itself was never wrong.

A multi-write check's own post-fix recheck (`CheckOrchestrator._mark_resolved_and_get_still_present`) must not then relabel an already-aborted violation `[FIXED]` just because a fresh `check()` no longer detects it — the very external edit that caused the abort can just as easily be the reason the violation is gone (e.g. the concurrent editor already renamed the function to something compliant), and this run's own write never actually landed. That recheck now skips `mark_fixed()` for any violation already carrying a rejected/errored/failed/aborted outcome from the check's own per-violation loop, the same precedence this decision requires of every other terminal outcome.

## Consequences

- A concurrent edit to a file `--fix` is currently processing — from an editor, or from any process outside this tool's own per-file fix lock — is never silently discarded. The affected violation is reported `[FIX ABORTED]` with a non-zero exit code instead.
- `atomic_write_text()` now performs one additional full read of the target file per write, immediately before the rename. Every check's `fix()` already reads the file at least once to compute its edit, so this is the same order of I/O cost the write path already pays, not a new class of cost.
- `docs/audits/0002-behavioral-contract-audit-fix-engine.md`'s "not applicable" finding for ch. 3 concurrent modification is superseded by this decision; the audit report itself is annotated rather than rewritten, per this project's own convention for a later ADR revisiting an earlier audit conclusion (see `docs/audits/0007-behavioral-contract-audit-process-signals-parallelism.md`'s own "Update, ADR-0041" note for the precedent).
- Still not a true compare-and-swap: POSIX offers no primitive to atomically compare a file's content and rename over it in one step, so a change landing in the gap between this check's own read and the rename itself (temp-file `chmod` plus `replace()`) remains theoretically possible — the same irreducible gap `docs/audits/0002` already noted "a real fix" would still have. This decision narrows that gap as far as the existing write pattern allows; it does not add a daemon, file lock, or other mechanism to close it further, matching the issue's own stated non-goal.
- Rolling back an already-committed, independent fix to a _different_ file when one file's fix aborts remains out of scope, unchanged from this project's existing per-file fix isolation — the issue's own stated non-goal.
